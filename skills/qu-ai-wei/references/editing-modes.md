# 按任务选择编辑方式

## 适用边界

用户的授权范围、目标语体和事实保护适用于所有参考。没有“真人文本一律不改”的分支，也没有必须保留一处毛边或输出报告的配额。下面是选择表达方式的线索，不是对作者身份的分类。

## 常见场景

| 场景 | 保留什么 | 常见改动 |
|---|---|---|
| 个人叙述、访谈、文学表达 | 人称、方言、引语、犹疑与有意节奏 | 按用户要求解决重复或不清楚处；不编造生活细节。 |
| 日常消息与社交文本 | 真实语气、交往关系和必要情绪 | 去掉无关客套或模板语，避免改成正式报告。 |
| 商务、工作邮件 | 行动、责任、日期与专业程度 | 把抽象承诺改清楚，但不能编具体人/时间/指标。 |
| 学术、工程报告 | 术语、量纲、测量条件、推断与结论层级 | 减少空泛评价，保持可复核条件；被动句、进行+动词等可按语义保留。 |
| RTL/程序注释 | 接口、符号、逐拍行为和授权代码区域 | 只改被授权的自然语言；注释错误需依源码确认，不能从润色推导新功能。 |
| 品牌、自媒体 | 目标受众、产品事实和有意风格 | 按场景处理口号和节奏，不把社交表达规则强加给品牌文案。 |
| 公文、合同、应试文本 | 固定术语、规定格式与论点 | 保守修改表达；不把专业判断伪装成语言修改。 |

只从上下文无法判断且确实影响交付时，才询问用途。否则采用原文已有语体；仍不明确时使用中性书面表达，不强加社交口语。

## 只改一部分

保持用户指定保留的段落、引语和格式。整篇交付时，可原样带回未授权修改的内容；不能顺便统一用词、编号或语气。代码注释修改前后应核对可执行部分完全相同。

## 原文存在问题

破损、缺词或事实疑点不应靠猜测“修顺”。可以修复明确的语法残缺；涉及技术事实、金额、人物态度或论点方向的歧义，保留不确定性并指出具体问题。只有用户明确要求补充或核验事实时，才进入相应取证任务。

## 可选修改说明

用户要求时列最重要的真实变动，例如“删去重复的结论；保留原有 2.3 mV 和待板测条件”。需要前后对照则引用原句和改句；不要把没发生的修改、未清点的数量或推测作者身份写进报告。用户只要终稿时省略说明。
