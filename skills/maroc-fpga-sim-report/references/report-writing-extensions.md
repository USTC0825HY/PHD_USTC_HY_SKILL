# 手册瘦身与流程图写法

## 何时加载这份参考

当用户反馈：
- 手册臃肿
- 结构不清
- case 设置思路不清
- 信号流检查思路不清
- 需要 Mermaid 流程图
- 需要把 `xsim` 实操写在最前面

## 推荐主线

一份可读的 MAROC 仿真手册，主线应当是：
1. 先操作
2. 再定位当前仿真层
3. 再讲信号链
4. 再讲 case 怎么设
5. 再讲看哪些信号
6. 最后给结果与签核

如果内容太多，优先删：
- 已被后文表格完全覆盖的重复说明
- 多次重复的波形常识
- 相同结论的不同表述
- 重复出现的脚本路径清单

不要删：
- 当前层验证边界
- case 合同
- 关键 checker/counter/log
- 最终签核结论

## 当用户说“case 不清晰”时必须补什么

至少补 4 个件：
1. 正例设置流程图
2. 反例设置流程图
3. 信号观察流程图
4. case 对照表

case 对照表至少含：
- case 名
- 设置/改包思路
- 第一优先看哪些信号
- 第二优先看哪些信号
- 最终 pass/fail 判据

## 当用户说“信号流不清晰”时怎么写

不要只列信号清单。

应写成分层顺序：
1. 输入入口
2. parser 控制
3. header/payload 抽取
4. drain 到 slowcontrol
5. slowcontrol 启动与 busy/done
6. 串行移位输出

## `o_sc_dout` 串行签核怎么写

如果用户要确认最终码流正确，不要只写“TB passed”。

必须明确：
1. 采样口径
   - 例如：`posedge o_sc_clk` 且 `o_sc_busy=1`
2. 原始对照源
   - `bits_829_case_*.txt`
3. 输出工件
   - timing compare CSV
   - summary CSV
   - compare report
4. 最终话术
   - “最终 `o_sc_dout` 串行码流与原始 fixture 逐 bit 一致”

## 典型 Mermaid 图

优先使用这些图，不要无节制堆图：
- 总体信号链图
- 单事务流程图
- 三层验证边界图
- 正例设置流程图
- 反例设置流程图
- 信号观察流程图

当三层边界图太拥挤时，拆成三张：
- `sim_parser`
- `sim_sc829`
- `top`

## `xsim` 实操章节怎么写

放在手册最前面时，只写：
1. 用哪个 `PS1`
2. 打开哪个工程/哪个 simset
3. 在 `xsim Tcl Console` 里 `source` 哪个 Tcl
4. 先看哪组波形

这一节不要混入完整理论推导。

## 模块级 USB/FIFO 手册补充

若任务是 `CY_driver_new`：
1. 先解释 bridge 定位，不是完整 USB stack
2. 早写接口表：
   - `00 -> EP2_IN -> 写 -> FPGA/DUT 驱动 FD[15:0]`
   - `11 -> EP8_OUT -> 读 -> FX2 驱动 FD[15:0]`
3. 显式写“总线方向”说明块
4. 显式写“`PKTEND` 不是另一拍数据”说明块

## 结尾签核写法

结尾至少包含：
1. 本层已经证明什么
2. 本层还不能证明什么
3. 是否建议进入下一层仿真或上板验证
